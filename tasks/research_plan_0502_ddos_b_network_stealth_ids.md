# Research Plan B: Network-Traffic Stealth and Classical DoS/IDS Contrast

Date: 2026-05-02

## Goal

This plan studies Mobius Injection from the network-security perspective. The key hypothesis is that Mobius-induced LLM/API traffic is difficult for classical network-layer DoS detectors to flag because it consists of valid application-layer requests generated by legitimate agent containers.

This plan also includes a controlled comparison with classical DoS patterns such as SYN flood and high-rate HTTP request flood. These baselines are used only inside an isolated local lab network to demonstrate the layer mismatch between traditional network DoS and agent-induced LLM resource exhaustion.

## Core Claim

Traditional DoS traffic often creates obvious packet-level or connection-level anomalies. Mobius traffic can be stealthier at the network layer because:

- source identities are legitimate victim-side agents;
- connections are normal HTTP/API sessions;
- request payloads are semantically plausible LLM prompts;
- traffic rate can be tuned to avoid simple thresholds;
- resource exhaustion happens at the model/API layer rather than at the TCP handshake layer.

## Research Questions

- **RQ-B1:** How different does Mobius traffic look from benign agent traffic at the network-flow level?
- **RQ-B2:** Can classical IDS or network DoS detectors distinguish Mobius traffic from normal LLM-agent traffic?
- **RQ-B3:** How does Mobius traffic compare with classical SYN flood and HTTP flood baselines?
- **RQ-B4:** Which features are necessary to detect Mobius: packet-level features, HTTP/API features, or agent-component features?

## Experimental Setup

### Local Network Topology

Use an isolated Docker network:

```text
agent containers
  -> local network bridge
  -> proxy/logger
  -> local LLM server
```

Optional monitoring containers:

- packet capture sensor;
- IDS container;
- flow exporter;
- reverse proxy with access logs.

All experiments must remain local. The target is always the local LLM server or a local dummy HTTP service.

### Traffic Classes

Collect four classes of traffic:

1. **Benign agent traffic**
   - normal tasks without injection;
   - normal LLM API calls;
   - no Mobius loop.

2. **Mobius stealth traffic**
   - poisoned agent;
   - low or moderate intensity;
   - normal LLM API path and payload shape.

3. **Mobius aggressive traffic**
   - poisoned agent;
   - high intensity;
   - still valid HTTP/API traffic.

4. **Classical DoS baseline traffic**
   - SYN-flood-like connection pressure against a local dummy service;
   - HTTP-flood-like high-rate requests against a local dummy service or local LLM endpoint;
   - generated only with explicit local rate caps and experiment windows.

Do not include commands or procedures that can be directly reused against third-party systems in the paper text or scripts.

## Observability Layers

### Packet / Flow Layer

Features:

- packets/sec;
- bytes/sec;
- flows/sec;
- connection attempts/sec;
- TCP flags distribution;
- SYN/ACK ratio;
- average flow duration;
- source/destination tuple diversity;
- retransmissions and resets.

Expected:

- classical SYN flood should be obvious at this layer;
- Mobius stealth may look close to benign agent traffic.

### HTTP / API Layer

Features:

- requests/sec;
- endpoint path;
- request body size;
- response body size;
- status code distribution;
- latency;
- keep-alive behavior;
- user-agent or client library identity if available.

Expected:

- aggressive Mobius may show elevated API request rate;
- stealth Mobius may remain within normal per-agent ranges;
- HTTP/API logs are more useful than packet-only features but still lack component-causality.

### Agent / Component Layer

Features:

- component invoked;
- component class S/M/C;
- component ADD/EDIT event;
- tool-call sequence;
- resource vertex reached;
- trigger source;
- Mobius closure indicators.

Expected:

- ACE should separate Mobius from benign traffic earlier than packet/flow or HTTP-only detectors.

## IDS / Detector Baselines

### B1. Flow Threshold Detector

Simple rules over flow volume:

- packets/sec threshold;
- flows/sec threshold;
- bytes/sec threshold;
- SYN/ACK anomaly threshold.

Purpose:

- should detect classical SYN flood;
- should miss or delay stealth Mobius.

### B2. HTTP Rate Detector

Rules over application requests:

- requests/min per container;
- requests/min per endpoint;
- p95 latency increase;
- failed request rate;
- body-size anomaly.

Purpose:

- may catch aggressive Mobius;
- may miss stealth Mobius and normal-looking recursive calls.

### B3. Existing IDS Tooling

Use a local IDS in observation mode if available, such as Suricata/Zeek-style flow logging. The point is not to tune IDS signatures exhaustively. The point is to show whether off-the-shelf network visibility sees Mobius as anomalous.

Purpose:

- compare alerts for classical DoS vs Mobius traffic;
- document alert absence or low severity for valid LLM API calls.

### B4. ACE Component-Layer Detector

Use ACE features from the defense plan:

- component mutation;
- instruction density shift;
- execution-affordance delta;
- cross-component propagation;
- temporal persistence;
- runtime graph recurrence.

Purpose:

- show that component-layer visibility is required for early detection.

## Experiment B1: Classical DoS vs Mobius Traffic Separability

### Procedure

Collect traffic traces for:

- benign agent runs;
- Mobius stealth runs;
- Mobius aggressive runs;
- controlled local SYN-flood-like baseline;
- controlled local HTTP-flood-like baseline.

### Metrics

- detector TPR/FPR per class;
- alert count;
- time to alert;
- packet/flow feature distance from benign baseline;
- HTTP/API feature distance from benign baseline.

### Expected Result

Classical DoS should be easy to separate at packet/flow layer. Mobius stealth should be closer to benign agent traffic and require application or component-level visibility.

## Experiment B2: Network-Layer Stealth of Mobius

### Procedure

Run Mobius with stealth, moderate, and aggressive profiles. Compare each profile with benign agent traffic under the same task set.

### Metrics

- request rate overlap with benign distribution;
- bytes/sec overlap with benign distribution;
- p95 latency impact;
- IDS alert rate;
- successful hidden calls before first alert.

### Expected Result

Stealth Mobius should stay under simple network thresholds while still accumulating non-trivial tokens and cost.

## Experiment B3: What Feature Layer Detects Earliest?

### Procedure

For each run, compute detection time under:

- flow threshold detector;
- HTTP rate detector;
- IDS alerts;
- ACE detect-only.

### Metrics

- TTD stage:
  - before component write;
  - after component write but before trigger;
  - after trigger;
  - after visible resource degradation.
- TPR/FPR;
- residual tokens before detection;
- residual requests before detection.

### Expected Result

ACE should detect at post-grafting / pre-trigger stage, while network and HTTP detectors detect only after visible runtime resource use, if at all.

## Outputs for Paper

The expected output form of Plan B is a layer-mismatch evidence chain:

3. a detection-timing figure showing that network/API detectors detect late, while component-layer signals detect earlier.

### Main Finding Statement

Plan B should support the following paper finding:

> Mobius-induced traffic is application-valid and network-stealthy compared with classical SYN/HTTP flood traffic; effective early detection requires agent-component visibility rather than packet-only monitoring.

## Safety and Isolation

- All classical DoS baselines must target only local dummy services or local LLM endpoints in an isolated Docker network.
- Use strict rate caps and short windows.
- Do not include reusable attack commands in the paper.
- Keep the purpose clear: comparing observability layers, not developing better network attacks.
